# ADR-0001: デバイスからサーバへの記録の経路

- 状態：承認
- 日付：2026-11-15

## 背景

- ESP32 は部室に常設する。部室の Wi-Fi は eduroam だけで、大学アカウントの認証情報をデバイスに置きたくない。
- ESP32 には携帯回線がなく、通信手段は Wi-Fi と Bluetooth のみ。
- 合図（Press）は遅れてはいけない（目安 50ms 以内）。

## 選択肢

| 選択肢 | 良い点 | 気になる点 |
| --- | --- | --- |
| A. 計測画面を ESP32 が配信し、スマホが記録を運ぶ | ファームの通信が単純 | 画面が 2 つになる。ESP32 配信のページ（HTTP）でログイン状態を持ちにくい |
| B. 記録を ESP32 にため、自宅 Wi-Fi で後から送る | 練習中はネット不要 | 部室に常設すると自宅 Wi-Fi に届かない |
| C. 練習中は常時テザリング。ESP32 がセットごとに直接送る | 画面が Web アプリ 1 つで済む。記録がすぐ見られる | 部室でスマホの電波が必要。合図はデバイス側で出す必要がある |
| D. ESP32 を eduroam につなぐ | 常時接続 | 大学アカウントをデバイスに保存することになる。規程上の確認も必要 |

## 決定

C を採用する。練習中は iPhone のテザリングを常にオンにし、ESP32 はセットが終わるたびに記録を HTTPS で API に送る。送れなかった記録は LittleFS の再送キューにため、つながったら古い順に再送する。

## 理由

- 画面を Web アプリ 1 つにでき、ESP32 側の画面配信（Mixed Content の問題を含む）が不要になる。
- 再送キューと冪等キー（clientSetId）を組み合わせれば、電波が途切れても記録は欠けず、重複もしない。
- D は認証情報の漏えいリスクが大きい。

## 影響

- 合図はデバイスのブザーと LED で出す（クラウド経由でスマホから鳴らすと遅れる）。
- スマホは iPhone を前提とし、「互換性を優先」をオンにして 2.4GHz でテザリングする。
- 部室で電波が入らない日が多ければ、B（後送り）を組み合わせる形を再検討する。
