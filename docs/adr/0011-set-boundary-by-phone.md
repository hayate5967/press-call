# ADR-0011: セットの開始と終了をスマホのボタンで決める

- 状態：承認
- 日付：2026-11-21

## 背景

これまでデバイスは、センサーの動きだけでセットの区切りを決めていた（FR-D03）。始まりは「Top から下降に入ったとき」、終わりは「フェーズが変わらないまま 15 秒たったとき」。この方式には次の弱点がある。

- 最後のレップから 15 秒たたないとセットが終わらず、アプリに出るのが遅い
- ラックに戻して 15 秒以内に再開すると、2 セットが 1 つにつながる
- ラックから外すときの下向きの動きなどを、セットの始まりと取り違えるおそれがある

ADR-0002 の「判定はデバイス内で完結させる」が指すのは、センサーの加速度・速度から静止を見つけて Press 合図を出すことで、セットの区切りは含まない（2026-11-21 ユーザー確認）。区切りは合図ほど急がない（1〜2 秒遅れてもよい）ので、スマホから決めてもよい。

スマホからデバイスへ直接は送れない。Web アプリは https なので、デバイスの `http://bench.local` を呼べない（混在コンテンツ）。iPhone の Safari は Web Bluetooth にも対応していない。そのため、サーバを経由させる必要がある。

## 選択肢

| 選択肢 | 良い点 | 気になる点 |
| --- | --- | --- |
| A. 今のまま自動で区切る（待ち時間を調整できるようにする） | 操作がいらない。通信に頼らない | 上の弱点が残る |
| B. スマホのボタンで開始・終了（サーバ経由、デバイスが 1 秒おきに取りに来る） | 区切りが確実。取り違えがない | 毎セット 2 回押す。1〜2 秒遅れる。つながらないと届かない |
| C. デバイスのボタンで開始・終了 | 通信に頼らない | バーを持つ前後にデバイスまで手を伸ばす必要がある |

## 決定

B を採用する。次の 2 つの安全策を組み合わせる。

1. **つながらないときは今の自動の区切りに戻る**：デバイスがサーバに一定時間つながらないあいだは、これまでどおりセンサーの動きでセットを区切って記録し、つながったら送る。記録を落とさないため
2. **押し忘れたら自動で終える**：記録中にバーが一定時間（目安 3 分）動かなければ、デバイスが自分でセットを終える。「終了」を押し忘れたときや、セットの途中で通信が切れたときに、記録が終わらないままにならないため

## 理由

- 区切りの誤りが記録の質に直接効く（つながったセットは速度の分析を誤らせる）。ボタンで決めれば確実になる
- 合図（静止の検知と Press）はこれまでどおりデバイス内で行うので、合図の遅れ（NFR-01）は変わらない
- テザリング元のスマホを手元に置いて使う前提なので、ラックから外す前と戻した後に押すのは無理がない
- つながらないときに自動の区切りに戻せば、電波が途切れても練習できる（NFR-04）を保てる

## 影響

- 要件定義書の FR-D03 を書き換え、Web アプリの要件に開始・終了のボタン（FR-V11）を足す。FR-S07（設定の取得）は、記録中も「開始・終了」を取りに来るよう変わる
- API に「デバイスの記録の状態」を置く場所（Web アプリが開始・終了を書き、デバイスが 1 秒おきに読む）を足す。データ設計にも列かテーブルが増え、本番に出すときマイグレーションが要る。具体的な形は実装のときに API 仕様書・データ設計に書く
- デバイスは記録中もサーバに問い合わせる。問い合わせはネットワークのタスクで行い、計測・合図のタスクを止めないこと（実機で計測の周期が乱れないか確かめる）
- ファームのフラッシュ使用量が約 96% のため、先にパーティションを変えて空きを作る（計画の 7 番）
- 見直す条件：押す手間が大きい・押し忘れが多いなら、A（自動）を既定にしてボタンを任意にすることを考える

## 追記（2026-11-21）：問い合わせは 5 秒おき、区切りはボタンを押した時刻で決める

1 秒おきでは問い合わせが多すぎる（ユーザー指摘）ため、ESP32 が指示を取りに来る間隔を 5 秒にする。開始を押してからラックから外すまでには時間があり、急ぐ必要はない。

ただし間隔を延ばすと、押してから ESP32 が気づくまで最大 5 秒かかり、すぐに下ろし始めると 1 レップ目が漏れる。そこで、セットの区切りは「ESP32 が指示を受け取った時刻」ではなく「ボタンを押した時刻」（サーバが記録する `started_at`・`stopped_at`）で決める。

- ESP32 は合図のために常にレップの動きを見ているので、直近 20 秒ほどのレップを手元にためておく
- 開始の指示を受け取ったら、`started_at` より後に始まったレップをさかのぼってセットに入れる
- 終了の指示を受け取ったら、`stopped_at` までのレップでセットを閉じる
- 時刻の比べ合わせには NTP で合わせた ESP32 の時計を使う

これで間隔は「アプリにいつ出るか」にしか影響せず、セットの中身は正確になる。上の「選択肢」「影響」にある「1 秒おき」は「5 秒おき」と読み替える。

## 追記（2026-11-21）：合図は記録中だけ鳴らす

実機で、記録中でないのにバーを動かすと Press 合図が鳴ることが分かった（ユーザー指摘）。ラックの準備で鳴るのは紛らわしいので、サーバにつながっているあいだは、セットの記録中だけ鳴らす（ブザーも LED も）。つながっていないあいだは、動きで区切るのでこれまでどおりいつでも鳴らす。

- 静止の判定そのものは常に続ける。指示が届く前のレップをさかのぼって記録に入れるため
- 開始を押してから指示が届くまで（最大 5 秒）は鳴らない。スマホが「記録中」になるか LED が点滅し始めてから、ラックを外す
- **さかのぼって入れたレップの反応時間・フライングは目安にならない**：指示が届く前のレップは、合図が鳴らなかったのに、反応時間とフライングの判定は記録される。5 秒以内に始めたレップが対象で、ふだんの使い方（押してからラックを外す）では起きにくい

## 追記（2026-11-22）：LED は付けない

使っている基板の GPIO2 には LED が付いておらず、外付けもしないことにした（ユーザー決定）。上の追記にある「LED（ゆっくり点滅・合図で光る）」は、付けたときだけの動きと読み替える。

- 開始の指示がデバイスに届いたかは、スマホの「記録中」の表示で確かめる。ラックを外すのは「記録中」になってから。デバイスから音は出さない（Press 合図と紛らわしいため）
- ファームの LED の処理（GPIO2）は残す。あとで GPIO2 に LED を付ければ、そのまま光る
