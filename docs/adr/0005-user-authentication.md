# ADR-0005: ユーザー認証の方式

- 状態：承認
- 日付：2026-11-15

## 背景

ログインと API の認証を自分で設計したい（特に JWT）。一方で、間違えると危険な部分は実績のあるものに任せたい。

## 選択肢

| 選択肢 | 良い点 | 気になる点 |
| --- | --- | --- |
| Better Auth などの全部入りライブラリ | 最も楽 | トークン設計の余地が少なく、学びにくい |
| Arctic（Google OAuth）＋自前 JWT | OAuth の検証はライブラリに任せ、トークン設計は自分で行える | 実装量は中くらい |
| すべて自前（パスワード認証を含む） | 学べる範囲が最も広い | パスワードの保存・総当たり対策・再設定まで必要。Workers 無料プランの CPU 10ms にハッシュ計算が収まらない恐れ |

## 決定

Google OAuth（Arctic、PKCE 付き）で本人確認し、その後は自前のトークンを使う。

| トークン | 形式 | 期限 | 保存場所 |
| --- | --- | --- | --- |
| アクセストークン | JWT（ES256、jose で署名） | 15 分 | ブラウザのメモリ |
| リフレッシュトークン | ランダム文字列（DB にはハッシュのみ） | 30 日 | HttpOnly・Secure・SameSite=Strict の Cookie |

リフレッシュトークンは使うたびに交換（ローテーション）し、使用済みのものが再び来たら盗難とみなして同じ系統をすべて失効させる。

## 理由

「複雑で危険な部分は実績のあるものに、学びたい部分は自分で」という線引き。パスワードを預からないので守るものも減る。

## 影響

- 本人の特定には Google の `sub` を使う（メールアドレスは変わりうるため）。
- 2 つのタブからほぼ同時に更新されたときの誤検知を避けるため、使用後 10 秒以内の再利用は猶予する。
